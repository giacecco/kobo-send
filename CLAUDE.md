# kobo-send

Bash pipeline + webhook that sends a file to a Kobo Clara 2E: `input --(pandoc)--> epub --(kepubify)--> .kepub.epub --(rclone)--> Google Drive folder`, which [KoboCloud](https://github.com/fsantini/KoboCloud) on the device syncs over WiFi.

URL/web-page input (as opposed to a file) is **not currently supported** — that branch existed in both `kobo-send.sh` and `server/kobo-webhook.ts` but was removed (its `claude -p` WebFetch-based extraction was unreliable and never confirmed fully working). See git history around the "delete URL branch" commit if reviving it.

The pipeline itself runs on an always-on Linux server, not on the Mac. The Mac and any iPhone (both via Shortcuts) are thin clients that `POST` to a webhook exposed through a Cloudflare Tunnel — neither needs pandoc/kepubify/rclone/`claude` installed locally. (Real server hostname and tunnel domain are intentionally not in this file — this repo is public. Check `~/.config/kobo-send/` on your own deployment, or your shell history, for the actual values.)

## Known fragility

This pipeline is not robust — it has broken in several different ways in normal use, each silently (no error surfaced to the user until something was manually sent and checked):
- Both Mac entry points (Automator Quick Actions for Finder and Safari) stopped working after a macOS update, with no deprecation notice — see the Automator/`NSServices` note below. Replaced by a Shortcut, which has its own rough edges (a one-time "Allow Running Scripts" opt-in for anything using `Run Shell Script`).
- The server's `~/.config/rclone/rclone.conf` is a single shared file across unrelated projects on that box — a `rclone config` run for a different project silently deleted this project's `kobocloud` remote, breaking every upload with no alert. A follow-on incident: the `rclone config create` command used to recreate that remote was left running (hung, never exited) for over a day afterwards, with the live OAuth access/refresh token sitting in plaintext in its command line — visible to any user on the box via `ps`. Killed once discovered; if you ever run `rclone config create ... token='...'` again, confirm the process actually exits.
- The server's `claude` CLI OAuth session used to expire and stop auto-refreshing, silently breaking every PDF conversion until manually re-authenticated (`claude login`) — now mitigated by switching to `ANTHROPIC_API_KEY` auth (see the Layout note on `~/.config/kobo-send/anthropic-api-key`), which doesn't expire the same way. Billed separately, at Anthropic API rates, from any Claude subscription the OAuth login would have used.
- **`claude -p` intermittently refused to convert PDFs on sensitive-but-legitimate topics — root-caused and mitigated, not eliminated.** In one test batch, 3 of 4 legitimate PDF sends failed with a plain-English refusal ("I can't complete the conversion — I'm blocked on reading the file...") instead of converting, different wording each time. Ruled out: server resource contention (CPU/memory/load confirmed healthy) and concurrency (re-ran the *same* file sequentially, no overlap, and still got inconsistent success/failure). The common thread: the failing file was a Meta blog post discussing cybersecurity, bioweapons/chemical risk, and government surveillance at length as policy commentary — legitimate content the requester already possessed, but the kind of subject matter that can trigger occasional model-level caution. Fix: added a reassurance clause to the PDF prompt (alongside the existing copyright one) stating that transcribing commentary/analysis of such topics isn't providing instructions or advocacy, and that the conversion is only reformatting for the requester's own more comfortable reading, not creating new content. Refined once more after an initial 3/3-success round, to generalize the topic list and sharpen the "why this is safe" framing — verified with 6 consecutive full-pipeline runs total against the exact file that had failed. This is a prompt-level mitigation, not a guarantee — a real send after this fix still hit the refusal once, then succeeded on an identical resend seconds later, confirming it's a genuine per-call flake rather than something deterministic about any specific file. `kobo-send.sh`'s PDF branch now retries the body-content `claude -p` call up to 3 times (same guards each attempt) before giving up, specifically because of this — don't remove the retry loop without another way to absorb this flakiness, since it's meaningfully better than making the sender manually resend. The three attempts also ladder different models explicitly (`--model haiku` → `sonnet` → `opus`, cheapest first) — see the next bullet for why an explicit `--model` matters at all, and the title/author bullet further down for why that ladder only applies to body content, not title/author detection. If refusals resurface on some other sensitive-topic document even after retries, extend the clause rather than assuming a new bug. The sentinel-guard and flock protections below still matter regardless — they contain *any* refusal cleanly, whatever triggers it.
- **`claude -p` calls with no `--model` flag silently ran on Opus 5 (the priciest tier) for every single PDF conversion.** Not discovered until the switch to `ANTHROPIC_API_KEY` billing made an unpinned default's cost a real concern instead of an abstraction — asked "what model is the script using" and had to check by asking `claude -p` to self-report its model ID. Fixed by pinning explicitly and, since then, laddering by cost — see the bullet above and the title/author-detection bullet below. Always pass `--model` explicitly in any script that shells out to `claude -p` — don't rely on the CLI's default, which isn't visible from the invocation itself and can change.
- **`rclone copy` silently overwrites a same-named file in Drive, with no error and (until recently) no log trace of it happening.** Confirmed in practice: sent 4 real files in one batch, 3 script runs logged "Done", but only 2 distinct files ended up in Drive — the most likely explanation is two of the sent articles produced the same extracted title, so the later upload silently replaced the earlier one. `kobo-send.sh` now logs `Uploaded: <kepub filename> (source: <original input>)` on every successful upload specifically so this is auditable after the fact — don't remove that line; before it existed, this failure mode was nearly undiagnosable (the run-level "Done: N file(s) sent" summary doesn't distinguish "N uploaded" from "N reached Drive as distinct files").
- **`rclone` is using its shared/default Google Drive `client_id`, which rclone has announced is being retired and will stop working sometime during 2026** — surfaced as a `NOTICE` on every `rclone copy`: "This remote uses rclone's shared Google Drive client_id, which is being retired... Create your own client_id to avoid interruption: https://rclone.org/drive/#making-your-own-client-id". This is a needed change soon, not yet done — every upload will break with no advance warning beyond this recurring notice once the shared client_id is actually shut off. Fix: create a dedicated Google Cloud OAuth client_id/secret for this project and reconfigure the `kobocloud` rclone remote to use it (see the linked rclone docs).
- Debugging any of this requires SSH access to the server, reading `journalctl --user -u kobo-webhook.service`, and manually re-running `rclone lsf`/`rclone config`/`claude -p` to isolate which of several independent moving parts (Mac client trigger, webhook, rclone auth, claude auth) actually failed — there's no single health check or alerting for any of it.

Treat "it's been quiet" as "unknown," not "working" — nothing here pages anyone when it breaks.

## Layout

- `kobo-send.sh` — the whole conversion pipeline. Deployed to `~/.bin/kobo-send.sh` **on the server**, invoked by the webhook. Not run from this repo checkout, and no longer installed on the Mac.
- `kobo-send-client.sh` — thin curl-based client. Deployed to `~/.bin/kobo-send-client.sh` **on the Mac**; posts a file to the webhook and lets the server do the work. Reads the bearer token from `~/.config/kobo-send/webhook-token`. Its `http(s)://` branch (POSTs JSON) is currently dead code — the webhook rejects any JSON POST with a 400 now that URL input isn't supported — but left in place in case URL support is revived.
- `kobo-send.conf.example` — template for `~/.config/kobo-send/config` **on the server**, which holds the real, untracked `GDRIVE_REMOTE`/`GDRIVE_FOLDER_ID`/`PURGE_OLDER_THAN` values. Never commit real values.
- `~/.config/kobo-send/anthropic-api-key` — untracked, server-only, `chmod 600`, holds a plain Anthropic API key. `kobo-send.sh` exports it as `ANTHROPIC_API_KEY` before invoking `claude -p`, so the PDF-conversion step authenticates that way instead of via `claude login`'s OAuth session (which used to expire silently — see Known fragility). Not created by any example/template file; write it by hand (`umask 077; cat > ~/.config/kobo-send/anthropic-api-key`) on the server.
- `server/kobo-webhook.ts` — the webhook itself (Bun/TypeScript). Bearer-token-gated, accepts a file (multipart) — a JSON POST (the old URL path) now gets a 400. Queues the job, returns immediately (HTTP 202) since Cloudflare's edge times out connections after ~100s — the actual `kobo-send.sh` run happens detached, in the background. Deployed to `~/.bin/kobo-webhook.ts` on the server, run via `bun run`.
- `server/systemd/*.service` — systemd **user** units (`~/.config/systemd/user/`) for the webhook and the `cloudflared` tunnel process. Require `loginctl enable-linger $USER` so they survive logout/reboot without an active session.
- `server/cloudflared-config.yml.example` — template for `~/.cloudflared/config.yml` on the server; real file has an account-specific tunnel ID and credentials path, so isn't committed.
- No `automator/` folder anymore — the Mac file-send entry point ("Send Files to Kobo") is a macOS Shortcut now, not an Automator Quick Action. No repo folder for it, or for the iOS Shortcut — they're built directly in the Shortcuts app (see README's Setup section) since Shortcuts has no plain-text export format worth tracking. (The "Send Page to Kobo" URL-sending Shortcut that used to exist alongside it was deleted along with the URL branch.)

## Key implementation details worth knowing before touching this

- **kepubify's output filename is not predictable.** It has varied across versions (`<stem>.kepub.epub` vs `<stem>_converted.kepub.epub`), so the script globs for `${STEM}*.kepub.epub` rather than hardcoding it. Don't reintroduce a hardcoded suffix.
- **kepubify rejects `.kepub.epub` inputs** (`invalid extension ".kepub.epub"`), so `kobo-send.sh` detects already-kepub files and uploads them as-is, skipping both conversion steps. Don't route them back through pandoc/kepubify.
- **Two separate title-page mechanisms exist and both need suppressing**: pandoc's own title page (`--epub-title-page=false`) and kepubify's heuristic-triggered dummy first page (`--no-add-dummy-titlepage`). Removing only one leaves a blank/title page on the device.
- **pandoc can't read PDF.** PDF input goes through `claude -p` first (with a narrowly scoped `--allowedTools "Read"`, not a blanket permission bypass) to produce clean Markdown, stripping ads/nav/boilerplate, before rejoining the normal pandoc step.
- **PDF title/author detection and body-content conversion are two separate `claude` calls, deliberately not one.** A wrong-but-plausible title/author sails straight past every guard downstream (they only catch refusals/emptiness, not inaccuracy) — confirmed in testing, where Haiku picked a subheading ("The Path to a Positive AI Future") instead of the document's real title ("The Future is for Everyone") on a real test document. So: (1) a dedicated title/author call, always on Sonnet (never laddered down to Haiku), given only page 1's text — extracted locally via `pdftotext -f 1 -l 1`, capped to the first 20 lines so a dense/multi-column page 1 can't blow up the prompt — plus `pdfinfo`'s embedded metadata and the filename, in that priority order, never inventing beyond those three sources, never accepting a bare first name (e.g. "– Mark") as a full author; (2) a separate body-content call that's explicitly told NOT to produce a title heading or byline at all, laddered Haiku → Sonnet → Opus (3 attempts) since accuracy no longer rides on this call. That title/author call had no retry at all until a real send silently missed an author ("Sam Altman", present only in the filename) that a direct reproduction moments later found correctly on the first try — confirmed a one-shot flake, not a design flaw, since this call has no downstream guard and just silently degrades (no author, or a filename-derived title) with nothing in the log to show it happened. Now laddered sonnet → opus (2 attempts) too, retrying only on a malformed reply (no line matching `^TITLE:`) — a well-formed "NONE" answer is a valid result and shouldn't trigger a retry. `kobo-send.sh` prepends the Step-1 title/byline to whatever Step 2 produces, so the visible in-book heading always matches `--metadata` regardless of which tier the body conversion needed. One deterministic safety net stays regardless of model: `AUTHOR` is discarded unless it's at least two words. `TITLE`/`AUTHOR` are unsanitized and passed straight to `pandoc --metadata title=... --metadata author=...`; `STEM` (filesystem-sanitized) is used only for the filename — don't reuse `STEM` for `--metadata title`, a trailing `_` from `tr` leaked into the displayed title that way once. Watch for `"_by $AUTHOR_"` inside a double-quoted string — bash parses that as the variable `AUTHOR_`, not `$AUTHOR` plus a literal underscore; use `"_by ${AUTHOR}_"`.
- **The PDF prompt includes a "sensitive topics are OK to transcribe" clause, and it's load-bearing, not decorative.** Testing surfaced a real failure mode: `claude -p` intermittently refused to convert an otherwise-legitimate PDF that discussed cybersecurity, bioweapons/chemical risk, and government surveillance at length as policy commentary — same file, same command, inconsistent success/failure across repeated *sequential* runs (ruling out concurrency/resource contention as the cause). The clause explains that the conversion only reformats an article the requester already possesses into an ebook for their own more comfortable reading — no new content, no advice, no action beyond reformatting — and that the document's sensitive-topic discussion is commentary/journalism/analysis, not operational instructions, so transcribing it faithfully isn't itself providing instructions or advocacy. After adding this, 6 consecutive full-pipeline runs against the exact file that had failed roughly 3 of 4 times before all succeeded. If refusals resurface on some other sensitive-topic document, extend this clause (e.g. broaden the topic list, sharpen the "why this is safe" framing) rather than assuming a new, unrelated bug.
- **`claude -p` sometimes refuses instead of erroring** (e.g. over copyright concerns, or the unexplained Read-tool refusal noted in Known fragility) and writes prose about the problem to the Markdown file instead of failing loudly. Guarded three ways, all necessary — none alone has proven reliable: (1) a deterministic sentinel — the prompt tells claude to output exactly `CONVERSION_FAILED` on failure, and `kobo-send.sh` greps for that literal line; (2) a byte-count floor (under 300 bytes ⇒ failure) for short refusals; (3) a non-blank-line-count floor (under 8 lines ⇒ failure) for longer refusal prose that clears the byte floor — a real refusal ("I can't complete the conversion — I'm blocked on reading the file...") has slipped past both (1)-unaware old code and (2) before, so don't drop (3) either.
- **KoboCloud has no "delete source after sync" feature**, and there's no way from the client side to confirm the Kobo has actually pulled a file (that only shows in `get.log` on the device). The `PURGE_OLDER_THAN` cleanup at the top of `kobo-send.sh` is a time-based approximation, not a real sync confirmation — don't present it as more reliable than that.
- **`kobo-send.sh` serializes with a `flock`** (`${TMPDIR:-/tmp}/kobo-send.lock`) so only one conversion runs system-wide at a time — a multi-file Share Sheet send fires several webhook-triggered runs back to back, and without the lock they'd race each other's `claude -p`/`pandoc`/`rclone` calls. An overlapping run blocks and waits rather than failing.
- **Automator Quick Actions/Services (`NSServices`) are unreliable-to-dead on modern macOS (confirmed on 26.6.2)** — both the Safari "Send Page to Kobo" Service (whole-page action) and the Finder "Send to Kobo" Service (file action) stopped working, with no error or deprecation notice. The Finder one was especially deceptive: macOS's own process logs showed the workflow loading and "running" via `com.apple.automator.runner`, but the embedded `Run Shell Script` step never actually executed (no `curl`/`osascript` child process ever spawned) — it just silently did nothing. Don't recreate either as an Automator Service; don't trust "the workflow launched" as evidence it ran. Replaced by a macOS Shortcut (Share Sheet), built directly in the Shortcuts app per the README, not tracked in this repo.
- **"Send Files to Kobo" POSTs to the webhook directly** — `Repeat with Each` (over Shortcut Input) wrapping a `Get Contents of URL` call (Request Body: Form, one `file`-type field = Repeat Item). Form's File-type Value field tolerates a Shortcuts magic variable fine; it was the *JSON*-body table's Value-cell variable insertion that was flaky in testing (both drag-and-drop and Edit → "Insert Variable" failed) — moot now since the JSON/URL path is gone, but keep in mind if any Shortcut ever needs a JSON body again. Building a Shortcut's `Run Shell Script` action (used by `kobo-send-client.sh` for direct-CLI-style sends) requires a one-time opt-in first: Shortcuts app → Settings → Advanced → **Allow Running Scripts** (off by default; without it the action refuses to run with an explicit "scripting actions are disabled" error — unlike the Automator failure, at least this one is visible).
- **The `Repeat with Each` wrapper is what makes multi-file sends work.** A bare `Get Contents of URL` File-type field only accepts a single item — a multi-file Share Sheet selection handed to it directly is silently truncated to one file. Don't simplify the Shortcut by removing the repeat. (The webhook itself already handled one file per request/queued job correctly; the truncation was purely a Shortcuts-side issue.)
- Automator/Quick Actions (where still used) run with a near-empty `PATH`. `kobo-send-client.sh` only needs `curl` (built into macOS) so this matters less than it used to, but it still sets `PATH` explicitly for safety.
- `kobo-send.sh` runs on both macOS (if ever tested locally again) and Linux — it branches on `uname` for the notify() implementation (`osascript` vs `logger`/stderr) and PATH setup. Don't reintroduce a macOS-only assumption.

## Testing changes

There's no automated test suite — this is a personal utility script. To verify a change to `kobo-send.sh` or the webhook (substitute your own server host and tunnel domain):
```
ssh <server> '~/.bin/kobo-send.sh /path/to/test-file.pdf'               # direct pipeline test
curl -X POST https://<your-tunnel-domain>/send -H "Authorization: Bearer $(ssh <server> cat ~/.config/kobo-send/webhook-token)" \
  -F "file=@/path/to/test-file.pdf"                                     # webhook test
rclone lsf kobocloud: --drive-root-folder-id <id>                       # confirm the upload landed
ssh <server> 'journalctl --user -u kobo-webhook.service -n 50'          # check background job outcome
```
After editing `kobo-send.sh` or `server/kobo-webhook.ts`, remember to deploy both to the server (`~/.bin/kobo-send.sh`, `~/.bin/kobo-webhook.ts`) — that's what's actually running, not this repo checkout. Restart the webhook after changing it: `systemctl --user restart kobo-webhook.service` on the server. After editing `kobo-send-client.sh`, deploy it to `~/.bin/kobo-send-client.sh` on the Mac — that's what the Mac Shortcuts' `Run Shell Script` actions invoke.

**Deploy `kobo-send.sh` atomically — don't `scp` straight over the live file.** A plain `scp local ubuntu1.local:~/.bin/kobo-send.sh` overwrites in place, non-atomically; if the webhook happens to `exec` the script mid-write (a real collision, seen in practice — a queued job hit "syntax error near unexpected token" from reading a half-written file), that job crashes with no upload and no retry. `mv` on the same filesystem is atomic, so `scp` to a temp path on the server and `mv` into place instead:
```
scp kobo-send.sh ubuntu1.local:~/.bin/kobo-send.sh.new && \
ssh ubuntu1.local 'chmod +x ~/.bin/kobo-send.sh.new && mv ~/.bin/kobo-send.sh.new ~/.bin/kobo-send.sh'
```
